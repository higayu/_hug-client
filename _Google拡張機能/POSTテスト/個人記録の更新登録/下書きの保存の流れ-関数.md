# 個人記録（下書き）の保存〜POST の流れ

参照: `個人記録取得パラメータ.md`、編集ページHTML（`#form_id`）、`SaveHandler.js`、`ContactBookSaveHook.js`。

---

## 1. 画面・URL の段取り

### ⑴ 一覧（編集へ行く入口）

- URL 例: `contact_book.php?f_id={施設}&date={開始}&date_end={終了}&id={児童c_id}`
- 出席行の **編集ボタン**（`button.edit`）の `onclick` に、編集ページへのパスが含まれる（例: `location.href='contact_book.php?mode=edit&...'`）。

### ⑵ 編集ページ（フォームあり）

- URL 例: `contact_book.php?mode=edit&id={個人記録id}&cal_date={日付}&c_id={児童id}`
- クエリの `mode=edit` は **画面表示用**。実際の保存POSTではフォーム内 `hidden` の値が使われる（後述）。

---

## 2. フォーム全体像（編集ページ）

- **`#form_id`**
  - `action`: `https://www.hug-ayumu.link/hug/wm/contact_book.php`
  - `method`: `post`
  - `enctype`: `multipart/form-data`（画像ありのため）
- **保存種別を分けるボタン**（いずれも `type="button"` であり、素の submit ではない）
  - **下書き**: `class="btn draft"`、`value="1"`、`data-save-button`
  - **保護者に公開**: `class="btn save"`、`value="2"`、`data-save-button`
- **実submit**: `#real-submit-button` は `display:none`（ユーザー操作は上記ボタン経由でスクリプトが POST する）。

### 保存時に重要な hidden（例）

| name | 例・意味 |
|------|-----------|
| `mode` | `regist`（保存POSTではこれが送られる） |
| `id` | レコード id（編集対象） |
| `r_id` | 行・カレンダー側の id 等 |
| `f_id` / `facility_id` | 施設 |
| `c_id` | 児童 |
| `cal_date` | サービス実施日 |
| `csrf_token_from_client` | CSRF |
| `initial_timestamp` / `concurrent_edit_id` | 同時編集・競合検知用 |
| `state` | **保存直前に JS が書き込む**（下記） |

活動コメントは `textarea[name="note"]`、職員共有は `textarea[name="staff_note"]`。shadow 用に `note_hide` / `staff_note_hide` もある（保存フックで同期）。

---

## 3. ブラウザ上の処理の流れ（関数の役割）

### 3.1 保存ボタンクリック → `SaveHandler.handleSave(clicked_button)`

1. 二重送信防止（`is_saving`）。
2. 競合状態・上書きモーダルの分岐（`proceedToSave`）。
3. **`proceedToSave`**  
   - 通常: 先に **競合チェックAPI**（`initial_timestamp` 等を渡す）。`status === 'conflict'` ならモーダルで待ち。  
   - `status === 'ok'` または強制保存なら **`executeSave`** へ。

### 3.2 `SaveHandler.executeSave`（本番の POST 直前〜送信）

1. **`beforeSaveHook`**（個人記録では `contactBookBeforeSaveHook` = `ContactBookSaveHook.js`）
2. **`input[name="state"]`** に、**押したボタンの `value`** を代入  
   - **下書き保存** → `state = "1"`  
   - **保護者に公開** → `state = "2"`  
   → サーバーはこれで公開／下書きを区別している想定。
3. **`FormData(form)`** を作成し、次を追加:
   - `is_ajax_request` = `1`
   - 競合後の上書きなど: `force_overwrite` = `1`（該当時のみ）
4. **`fetch(form.action, { method: 'POST', body: formData })`**  
   - つまり **最終的な本文保存は常に `contact_book.php` への multipart POST**。

### 3.3 `contactBookBeforeSaveHook`（POST 直前の ContactBook 専用処理）

**同期的なテキスト処理**

- `note` の内容を WAF 避けのための文字列置換（`"` → `カンマ`、`or`/`like` など）し、**`note_hide` にコピー**。可視の `note` は送信直前 `disabled`。
- `staff_note` も同様に **`staff_note_hide` へ**。

**画像（任意・非同期）**

- 新規画像 Blob があれば `ajax_contact_book_img.php?mode=ajax_regist&...` へ **別POST**（`img1`〜`img4`）。
- 削除フラグがあれば `mode=ajax_delete` を **GET** で呼ぶ。
- これらが完了してから、上記の **`FormData` による `contact_book.php` POST** に進む（フックが Promise で直列化）。

---

## 4. レスポンスと画面遷移

- **`Content-Type: application/json`** かつ `status: 'ok'` → **一覧へ** `redirect_url_on_save`（設定では `contact_book.php?mode=list`）。
- **`status: 'conflict'`** → タイムスタンプ更新・競合モーダル。再保存時は `force_overwrite` 等の流れ。
- テキストで `ok` だけ返るケースもコード上フォローあり。

---

## 5. 拡張やバッチから真似する時の要点

1. **編集ページの HTML を GET** して **CSRF・`initial_timestamp`・各 hidden** を取る（単に一覧URLだけでは不足）。
2. 保存は **ブラウザと同じ**く  
   - （必要なら）画像 AJAX →  
   - `note`/`staff_note` の扱いを **本番と同じ**に（少なくとも **hide フィールドと置換** を揃えるのが安全）。  
3. **`state` を `1` にすれば下書き**、`2` なら保護者公開側の保存。
4. **`FormData` + `is_ajax_request=1`** を付ける（`SaveHandler` と同等）。
5. **`credentials: 'include'`** でセッションCookie必須。
6. 競合API・`force_overwrite` は本番の同時編集設定に依存するため、自動化では競合レスポンスのハンドリが必要になる場合あり。

---

## 6. `個人記録取得パラメータ.md` との対応

- 一覧の `id`（児童）・編集URLの `id`（個人記録レコード）・`c_id`・`cal_date` は、フォーム hidden と一致させる。
- `textarea[name="note"][data-field-key="note"]` が拡張 `editpage.js` で読んでいる活動内容フィールド。保存時はフックにより **`note_hide` 側が実質送信に使われる**点に注意。

## 個人記録一覧のhtmlのテーブルデータのみで編集画面の下書き保存ボタンのPOSTリクエストを再現可能か？
結論：一覧のテーブル“だけ”では再現できない
下書き保存ボタンと同じ POSTを組むには、編集画面の #form_id に載っている hidden・CSRF・同時編集用タイムスタンプ・本文フィールド等が必須ですが、一覧テーブルの列にはそれらが含まれていません。

一覧テーブルから取れるもの（例：個人記録一覧.html）
編集ボタンの onclick に、編集URLの核になるクエリがある
例: id=40121（個人記録レコードID）、cal_date=2026-05-16、c_id=99
行ごとのサービス実施日（1列目の日付）
児童名・施設名の表示（c_id / f_id の数値は、一覧セルだけでは一意に確定しない行もある）
data-record-id（例: 99-3-1-2026-05-16）のような識別子（仕様はサーバー実装依存）
これらは **「編集ページを開くための手がかり」**にはなるが、POST ボディそのものには足りない。

一覧に無く、POST 再現に必要なもの（編集HTML側）
下書きの保存の流れ-関数.md のとおり、実保存はざっくり次のような前提です。

区分	一覧だけで足りるか
state=1（下書き）

mode=regist 等の hidden
編集ページ GET が必要
csrf_token_from_client
編集ページ GET が必要
initial_timestamp / concurrent_edit_id
編集ページ GET が必要
r_id / facility_id 等の hidden
編集ページ GET が必要
note / staff_note（およびフック後の hide フィールド）
編集ページ上の現在値（＋フックと同じ加工）が必要。一覧の「活動内容」は空や要約で、本文と一致しないことが多い
画像がある場合
ajax_contact_book_img.php 等の別通信が絡む可能性
実務的なまとめ
「一覧テーブルだけ」→ 不可
「一覧で mode=edit の id / cal_date / c_id を拾う → 編集ページを GET → そこからフォームをパースして POST を組む」→ 可能（セッションCookie必須、競合APIや force_overwrite の扱いは別途）
そのため 個人記録保存Post.js を作るなら、一覧はエントリ抽取だけにして、必ず編集ページHTMLを1回取得する形が筋になっています。
